# Архитектура MVP

## Текущий выбор реализации

Один модульный TypeScript-сервис на Next.js, PostgreSQL и отдельное приватное объектное хранилище. Next.js выбран для нового серверного слоя и будущего кабинета; существующий Vite-прототип остаётся отдельным инструментом проверки UX. Переносим проверенные взаимодействия, а не подключаем доверие к его localStorage.

| Слой | Ответственность | Сейчас |
| --- | --- | --- |
| apps/web | HTTP, серверная сессия, валидация, кабинет/клиентский интерфейс | API M0/M1, вход, кабинет, редактор трёх типов блоков с приватным предпросмотром и диагностический журнал запросов; реальный сетевой Auth ещё не проверен |
| packages/core | Чистые правила документа, денег и клиентской проекции | Реализован; не зависит от Next, cookies и Auth SDK |
| supabase/migrations | Ограничения, права, атомарные операции | Начальная схема, идемпотентное создание, буквальный поиск, программа и транзакционный аудит трёх операций; без применения в облаке |
| Адаптер Auth/Data API | Проверенный субъект, запросы с правами вызывающего | Supabase SSR только на сервере, новый клиент на запрос |
| Файловый адаптер | Логический asset ID, разрешение чтения, короткая ссылка | Ещё не реализован |
| Пространственный модуль | Геометрия, размещение, коллизии, общий формат сцены | Пока в прототипе; production-контракт ниже |

Не вводим микросервисы, Kubernetes, Redis и очередь до появления соответствующей нагрузки. Обработка моделей и миниатюр позже выносится в ограниченный по ресурсам worker: загрузка → проверка → подготовка → готовность. HTTP-запрос не должен ждать конвертации большого файла.

## Запрос сотрудника

Браузер → same-origin API → проверка актуального пользователя Auth → строгая схема запроса → запрос в PostgreSQL с JWT этого пользователя → RLS/проверяемая операция → подтверждённый результат.

Сервер не подменяет обычного сотрудника административным ключом. Идентификатор агентства из URL или тела — адрес ресурса, а не доказательство доступа. Роль берётся из действующего участия в базе. Метаданные пользователя и устаревшая роль внутри JWT не являются источником полномочий.

Чтение разрешено RLS. Прямые INSERT/UPDATE/DELETE таблиц для пользователей запрещены; запись идёт через короткие SQL-операции. Привилегированные функции находятся в неэкспонируемой схеме, имеют фиксированный пустой search_path, явную проверку субъекта/роли и узкий EXECUTE. Публичные RPC-обёртки работают как SECURITY INVOKER. Обоснование — [ADR 0002](../adr/0002-identity-and-authorized-writes.md).

В начальном M1 страницы — оболочка без приватных данных в HTML. Компоненты получают данные через закрытые Route Handlers; обновление сессии и запись cookies происходят там. Серверные компоненты не читают Auth, поэтому proxy refresh на этом срезе не нужен. При переносе приватного чтения в SSR требуется отдельно реализовать proxy/cookie/cache-поток по текущей документации и проверить отсутствие кеширования сессий.

Важно: Data API Supabase может быть вызван и вне нашего HTTP API. Поэтому правила владения, валидность документа и проверка ревизии продублированы в базе. Origin защищает браузерную cookie-сессию нашего API, но не заменяет эти правила. Лимиты частоты и общие квоты необходимо поставить также на прямые входы до внешнего пилота.

## Согласованность

Черновик имеет монотонную revision. Запись блокирует разрешённую строку, сравнивает expectedRevision и изменяет документ в транзакции. Устаревшая версия получает конфликт. Повтор после неизвестного результата сначала читает серверную ревизию; слепой повтор с новым номером запрещён.

Будущая публикация должна атомарно проверить ожидаемую ревизию и закрепить клиентский документ, бренд, версии сцен и файлов. Поле «актуальный выпуск» переключается только после готовности всех обязательных ресурсов. Неизменяемый выпуск не читает живую внутреннюю смету, текущий логотип или новый план зала. Текущая функция core строит безопасную проекцию, но операция публикации в БД/API ещё отсутствует.

## Пространство

Единственный документ расстановки содержит версию помещения и предметы в физических единицах. План, объём и прогулка — три представления этого документа, не три независимых массива координат. Производные коллизии, посадка, миниатюры и навигационные данные можно пересоздать. Пин версий исходных ресурсов обязателен.

Three.js загружается только в пространственной области и при запросе клиентом. Материалы простые. Постоянные ссылки на подписанные файлы в сцену не записываются; доступ получается через asset ID и проверяемый файловый адаптер. См. [пилот зала](SPATIAL_PILOT.md).

## Развёртывание и переносимость

Next.js поддерживает обычный Node.js и Docker; в сборке включён standalone. При самостоятельном размещении нужны reverse proxy, TLS, корректное ограничение тела запроса и приватное кеширование. Это не требует Vercel. [Официальное руководство](https://nextjs.org/docs/app/guides/self-hosting).

Конфигурация Supabase остаётся серверной; NEXT_PUBLIC для неё сейчас не используется. SDK закреплены точными версиями и lock-файлом. Пользователь продукта имеет собственный principal ID с сопоставлением провайдеру Auth. Это уменьшает связанность, но не делает миграцию автоматической: auth.uid, RPC-клиент, ключи, сессии, почта, файлы и резервные копии требуют отдельного перехода.

Текущий бесплатный путь — локальная разработка; удалённый Supabase возможен только для синтетических проверок. Production-провайдер не выбран. Подробности и ограничения — [инфраструктура](INFRASTRUCTURE.md).

## Публичные адреса и кабинет

Целевой выпуск размещается на поддомене платформы, кабинет — на отдельном служебном host. Wildcard DNS/TLS и серверная таблица разрешённых host → проект/выпуск появятся вместе с M2; сейчас subdomain routing отсутствует. Заголовок Host и похожее имя агентства не доказывают доступ. Приватный выпуск дополнительно требует grant.

Сотруднические cookies остаются host-only: не задаём общий Domain для всех агентских/клиентских поддоменов. APP_ORIGIN защищает изменения кабинета точным origin; SameSite не заменяет эту проверку между соседними поддоменами. Клиентская сессия имеет отдельную область и не наследует роль сотрудника. Кеш не смешивает host, выпуск и доступ; приватные ответы пока вообще не кешируются.

Собственные поддомены агентств — после пилота: подтверждение владения DNS, уникальная привязка, выпуск/обновление сертификата, удаление привязки и защита от повторного захвата. Пользовательский домен не даёт права внедрять код в кабинет платформы.
