# API M0 и начального среза M1

Обновлено 7 ноября 2026 года. Реализованы маршруты cookie-входа/выхода/сессии и приватных черновиков, unit-проверки HTTP-границы и SQL-проверки операций. Полная интеграция с работающими Supabase Auth/PostgREST ещё не выполнена. Signup, восстановление пароля, приглашения и публичные клиентские маршруты отсутствуют. Нельзя получить доступ обходным заголовком, демонстрационным PIN или переданным user ID.

## Общий контракт

JSON по same-origin HTTP. Приватные ответы, включая ошибки: Cache-Control: private, no-store; Pragma: no-cache; Expires: 0. Ошибка имеет форму {"error":"код"}, без текста SQL/SDK и секретов.

Для приватных маршрутов нужен подтверждённый пользователь Supabase Auth в серверной cookie-сессии. На каждый запрос создаётся свой клиент с publishable key и правами пользователя. getUser проверяет пользователя через Auth. Состояние участия проверяет БД, а не cookie. Эти требования ещё предстоит пройти реальным интеграционным тестом. [Серверный Auth](https://supabase.com/docs/guides/auth/server-side/nextjs).

POST/PATCH требуют точный Origin из APP_ORIGIN; cross-site Fetch Metadata отвергается. Content-Type — application/json. Проверяется фактический поток байтов даже без Content-Length: по умолчанию 300 KiB, создание агентства 8 KiB. База дополнительно ограничивает JSON-документ 512 KiB в своей сериализации. Это пределы транспортного среза, а не обещанные тарифные лимиты. Состав JSON строгий: нельзя передать роль, владельца или время изменения.

| Метод и путь | Вход | Ответ |
| --- | --- | --- |
| GET /api/health | Нет | 200 {status, service, version}; только живость процесса, без проверки базы |
| POST /api/auth/sign-in | {email,password}, Origin | 200 {user:{id,email}} и серверные cookies, без токенов в JSON |
| GET /api/auth/session | Cookie-сессия | 200 {user:{id,email}} после getUser |
| POST /api/auth/sign-out | Origin | 200 {signedOut:true}; выход из текущей браузерной сессии |
| GET /api/agencies | Сессия | 200 {agencies:[{id,name,created_at}]} только доступные |
| POST /api/agencies | {name} | 201 {id}; агентство и owner созданы атомарно |
| GET /api/proposals?agencyId=UUID | Сессия, агентство, необязательные q/cursor | 200 {proposals:[{id,agency_id,title,revision,updated_at}],nextCursor} |
| POST /api/proposals | {agencyId,creationKey,title?,document?} | 201 {proposal}; новая revision = 0, повтор возвращает существующий документ |
| GET /api/proposals/UUID | Сессия | 200 {proposal} с документом |
| PATCH /api/proposals/UUID | {expectedRevision,title,document} | 200 {proposal} с новой revision |

Поля ответа proposal: id, agency_id, created_by, title, document, revision, created_at, updated_at. created_by — внутренний UUID принципала, не email. Даты — серверные ISO timestamps. Идентификаторы строк БД имеют тип UUID; HTTP-схемы нормализуют входные UUID. Контракты документа заданы в packages/core и продублированы ограничениями SQL.

## Создание и сохранение

Создать минимальный черновик: {"agencyId":"UUID","creationKey":"НОВЫЙ_UUID"}. Заголовок по умолчанию пустой, документ — {"schemaVersion":1,"blocks":[]}. Обязательная анкета события отсутствует.

PATCH передаёт полное тело текущего документа и ревизию, которую видел редактор. Запрос с expectedRevision = 3 успешно превращает 3 в 4. Второй запрос с 3 получает 409 и не меняет состояние. Сначала сохраняется новая ревизия, затем UI вправе показать подтверждение. Если ответ потерян, редактор читает текущее состояние; автоматически менять expectedRevision и перезаписывать его нельзя.

RPC записи: create_agency(agency_name); create_proposal(agency_id, proposal_title, proposal_document, creation_key); save_proposal_draft(proposal_id, expected_revision, new_title, new_document). Создатель и роль не передаются. Операции возвращают ровно одну созданную/обновлённую запись; неожиданный результат не принимается за успешное сохранение.

creationKey ограничен агентством и текущим автором. Повтор с тем же исходным содержимым возвращает тот же документ, включая его последующие правки; ничего не перезаписывает. Смена исходного содержимого под тем же ключом даёт 409 creation_key_reused. Проверка роли действует и при повторе. Старая RPC-сигнатура без ключа удалена миграцией; внешних потребителей этого неопубликованного контракта пока нет.

Список возвращает до 50 строк, сортировка updated_at DESC + id DESC. nextCursor=null означает конец; иначе курсор передаётся следующим запросом с теми же фильтрами. Время в курсоре сохраняет микросекунды БД. q — буквальная подстрока названия без учёта регистра: SECURITY INVOKER search_proposals(agency_id,search_query) использует параметризованный strpos и RLS. Знаки *, % и _ не становятся шаблоном. Сетевая совместимость RPC/фильтров PostgREST требует интеграционного теста.

Login принимает не более 8 KiB, email до 254 и пароль до 1024 символов. Ошибка неверной пары возвращается без раскрытия наличия аккаунта; 429 обозначает ограничение попыток Auth. Приложение не реализует собственный password storage. До внешнего пилота нужны прикладной rate limit, настройка доставки/восстановления и полный цикл refresh/logout. Выход не является обещанием мгновенного аннулирования скопированного access JWT; строгая проверка отозванной сессии остаётся частью security gate.

## Ошибки

| Код HTTP | Примеры error | Реакция интерфейса |
| --- | --- | --- |
| 400 | invalid_request, invalid_json, invalid_proposal_id | Показать ошибку ввода, документ сохранить локально в пределах выбранной политики |
| 401 | authentication_required | Повторный вход |
| 403 | invalid_origin, verified_account_required | Не повторять запись автоматически |
| 404 | not_found | Ресурс отсутствует или недоступен; не раскрывать существование чужого КП |
| 409 | revision_conflict, agency_exists, creation_key_reused | Сравнить/перечитать существующее, не затирать |
| 429 | too_many_attempts | Подождать; не повторять автоматически |
| 413 / 415 | body_too_large / json_required | Объяснить ограничение запроса |
| 503 | workspace_not_configured, authentication_unavailable, storage_unavailable | Сервис не готов/временно недоступен; не показывать «Сохранено» |
| 500 | internal_error | Нейтральное сообщение; корреляция с безопасным журналом добавляется в M1 |

DELETE, изменение состава команды, выпуск и клиентский доступ ещё не реализованы. API без настроенного Supabase остаётся закрытым и отвечает 503; готовый интерфейс не заменяет реальную сессию.
