# Безопасность и эксплуатация

## Защищаемые данные и угрозы

Коммерческие расчёты, себестоимость, клиентские материалы, персональные сведения, доступ к предложениям и исходная геометрия. Основные противники: посторонний посетитель ссылки, участник другого агентства, клиент с разрешением только на просмотр, бывший сотрудник, утёкшая сессия, злоумышленник с файлом/ссылкой для загрузки. Ошибка нашего кода и неверная конфигурация — такие же реальные источники риска.

Администратор БД технически привилегирован. RLS не обещает защиту от владельца базы или утёкшего административного ключа. Для таких действий нужны ограниченные эксплуатационные учётные записи, MFA у операторов, отдельный доступ и аудит. Ни service_role, ни secret key в обычный клиентский запрос не входят.

## Реализовано M0

- RLS на всех прикладных таблицах, отсутствие анонимных grants, запрет прямой пользовательской записи.
- Текущий principal и действующее участие вместо доверия к user metadata или роли из тела запроса.
- Проверяемые SQL-операции, атомарный первый owner, серверное авторство, ревизия и транзакция сохранения.
- Строгие HTTP/SQL-форматы документа, лимиты фактического тела, целочисленные деньги, проверка переполнения.
- Серверный Auth-клиент на запрос, getUser, требование подтверждённого email, httpOnly/sameSite cookies, secure в production.
- Точный Origin для HTTP-изменений, отсутствие публичного кеширования приватного API, нейтральные ошибки.
- Явная клиентская проекция вместо передачи внутреннего документа и удаления нескольких секретных полей постфактум.

Наличие этих мер в коде не означает, что развернутая система проверена. До настоящих данных остаются перечисленные ниже обязательные работы.

## Границы, которые проверяем до пилота

| Граница | Необходимая проверка |
| --- | --- |
| Auth → API | Настоящий вход/выход, refresh, истечение сессии, неподтверждённый email, cookie-флаги и запрет публичного кеша с Set-Cookie |
| PostgREST → SQL | Те же атаки через Data API, правильные роли и grants после миграции, advisors на работающем стеке |
| Параллельность | Два независимых соединения сохраняют одну ревизию; успешно только одно, второе получает конфликт |
| Отзыв | Участие/принципал блокируются сразу для новых запросов; старый JWT не восстанавливает доступ |
| Клиент | Чтение не даёт запись, нельзя выбрать автора, неотправленный вариант недоступен менеджеру и другим клиентам |
| Файлы | Нельзя подставить чужой asset ID, MIME не принимается на веру, нет чтения произвольного URL сервером |
| Выпуск | Нет внутренних полей на любом уровне JSON/HTML, ресурсы закреплены; повтор не дублирует издание |
| Эксплуатация | Восстановление БД и объектов в чистое окружение, ротация ключей, журнал доступа без секретов |

Удаление пользователя в Auth не должно быть единственной операцией отзыва: до истечения JWT важно проверять актуальное участие и блокировку принципала. Первая операция закрытия доступа продукта — active=false/отзыв участия, затем управляемые операции провайдера.

## Файлы и браузер

До включения загрузки: приватный bucket, ожидаемый тип, максимальный размер и распакованный размер, ограничение количества/размеров текстур, запрет внешних URI в GLB/glTF, проверка контейнера, карантин до готовности. Пользовательские SVG/HTML не показывать как доверенный HTML. В MVP не принимать пользовательский JavaScript, CSS и произвольные шрифты без отдельного контура проверки. Значения токенов темы ограничиваются схемой.

Документы рендерятся как текст/проверенная структура. Использование unsafe HTML запрещено без санитарной обработки. До внешнего доступа добавить CSP под фактические ресурсы, HSTS на TLS-хосте, rate limits на Auth/API/Data API, лимит исходящего трафика и бюджеты файлов. Ограничения CDN и reverse proxy не заменяют проверку доступа в приложении.

Не логировать тело КП, смету, cookie, Authorization, секрет приглашения и подписанные URL. В M1 добавлен диагностический JSON-журнал девяти API-операций: фиксированное имя операции, серверный request ID, HTTP-статус и длительность. URL, query, заголовки, тела, email и текст исключения в него не передаются. Новый UUID возвращается в `X-Request-Id`; входящий одноимённый заголовок не используется. Health остаётся отдельной проверкой живости без этого журнала. Ошибка диагностического вывода не меняет подтверждённый результат записи.

Закрытая `app_private.audit_events` фиксирует успешное создание агентства, создание КП и сохранение: principal-автор текущей операции, агентство, действие, ID ресурса, ревизия, время и исход `succeeded`. Триггеры SECURITY INVOKER выполняются внутри существующих проверяемых операций; событие и изменение коммитятся или откатываются вместе. Сбой аудита откатывает запись. Повтор создания с тем же ключом не создаёт второе событие. Таблица имеет RLS и не имеет пользовательских grants/политик; owner/manager, другое агентство и anon не могут читать или менять её. RPC просмотра пока отсутствует. Владелец БД технически способен менять журнал — это не защита от привилегированного оператора.

Это начальный аудит трёх операций, а не полный журнал доступа: чтения и отказы видны только в диагностике API; прямые отклонённые вызовы Data API, действия операторов и будущие изменения команды пока не покрыты. SQL-события не связаны с HTTP request ID; прямые допустимые RPC-записи тоже создают событие. Сбор, защищённое хранение и срок ротации stdout, доступ оператора, срок хранения аудита и мониторинг его объёма требуют настройки до пилота. Наличие строк в локальной БД не доказывает доставку журналов в production.

## Резервирование и восстановление

Копия схемы в Git не является копией данных. Нужны независимые копии PostgreSQL и объектов хранилища с манифестом связей и хешей. Supabase отдельно предупреждает, что резервные копии базы не содержат сами Storage-объекты. [Руководство по резервным копиям](https://supabase.com/docs/guides/platform/backups).

Для пилота предлагаем RPO не более 24 часов и RTO не более одного рабочего дня, но это ещё не достигнутые показатели и не договорный SLA. Их принимают только после измеренного восстановления: чистая среда → схема/данные → объекты → сопоставление identities → ключи/доставка → тест доступа → тест старого выпуска. Копии шифруются, хранятся с ограниченным доступом и сроком; место хранения учитывается в российском контуре.

Перед миграцией провайдера: заморозка записи или контролируемый финальный перенос, сверка количества/хешей, смена маршрутизации, отзыв старых сессий и проверка повторного входа. Старый контур отключают после проверки результата и согласованного периода отката; нельзя молча вести две независимые базы записи.

## Виды доказательств

Core/HTTP тесты проверяют вычисления и локальные границы. PGlite исполняет настоящую SQL-миграцию PostgreSQL и тестирует RLS под authenticated/anon, а не под владельцем БД. auth.uid в тесте — фикстура уже проверенного субъекта, не реализация Auth. PGlite использует одно соединение; эти проверки не доказывают конкурентные транзакции, сетевой шлюз, почту или cookies. [Ограничения PGlite](https://pglite.dev/docs/).

Локальный Docker/Supabase не запущен. 13 ноября подключён отдельный внешний синтетический Supabase владельца: пять миграций, проверка CA/hostname клиентского TLS, RLS всех семи таблиц, отсутствие табличных grants anon. Анонимное чтение трёх public-таблиц и вызов create_agency через настоящий PostgREST вернули 401/42501. CLI advisors для этой БД на уровне warn не нашёл проблем; это не полный аудит Auth/инфраструктуры. Положительный вход, конкурентные соединения и восстановление пока не проверены. Реальные клиентские материалы не использовались.

## Нагрузка и сигналы

Для первой нагрузочной проверки предлагаем профиль: 2 агентства, до 5 одновременно сохраняющих менеджеров, до 20 читающих клиентов; это тестовая гипотеза, не предел тарифа. Измеряем p95 сохранения, долю ошибок/конфликтов, время до чтения страницы, вес первой загрузки и сцены, расход DB/Storage/egress. Чтение документа должно работать без загрузки 3D.

До старта нужны предупреждения о недоступности входа/сохранения/файлов, близости квот и ошибках резервирования. /api/health проверяет только процесс. Отдельная readiness-проверка зависимостей и операционный мониторинг ещё не добавлены. Обнаруженная утечка требует закрытия гранта/участия, сохранения следов, определения затронутой области и процедуры уведомления по применимым требованиям; нельзя просто очистить журнал.
