# Работа с проектом

Перед изменениями прочитать [контекст проекта](docs/PROJECT_CONTEXT.md), README и затрагиваемые документы.

## Принятие решений

- Работать как ответственный технический партнёр: самостоятельно исследовать варианты, проверять факты, выявлять риски и предлагать обоснованный выбор.
- Предложение владельца не является автоматически утверждённым требованием. Сначала выяснить задачу, сравнить альтернативы и обозначить последствия. Существенное изменение продукта, бюджета или архитектуры обсудить до реализации.
- Различать факт, требование, гипотезу, рекомендацию и принятое решение. Документирование гипотезы не переводит её в принятое решение.
- Исследование, ведение рабочих записей и обычные обратимые действия в согласованном объёме выполнять самостоятельно. Не превращать процесс в запрос разрешения на каждую техническую мелочь.
- Сохранять активную задачу и учитывать уточнения владельца. Изменившийся вывод исправлять также в документах, где осталось устаревшее предположение.

## Качество и безопасность

- Проверять изоляцию агентств, серверную авторизацию и разделение публичных материалов площадки и приватных данных КП.
- Реальные КП, сметы, персональные данные, пароли, ключи, исходные клиентские материалы и дампы не помещать в публичный репозиторий. Локальные приватные материалы хранить в `.local/`.
- Размещение данных и вспомогательные сервисы выбирать после анализа фактических потоков и требований российского запуска. Зарубежные эксперименты планировать на синтетических данных; не переносить туда реальные клиентские материалы.
- Не обещать точность геометрии, безопасность, производительность или соответствие закону без подходящей проверки. Автоматическая проверка согласованности размеров не подтверждает соответствие реальному залу.
- Предложения, опубликованные клиенту, связывать с конкретными версиями контента, оформления и сцены. Клиентские варианты отделять от оригинала менеджера.

## Реализация MVP

- Актуальная спецификация — [docs/mvp](docs/mvp/README.md); решения — [docs/adr](docs/adr/0001-runtime-and-deployment.md). Отличать реализованный M0 от будущего коммерческого объёма.
- Рабочие пакеты: apps/web (Next.js), packages/core (чистые правила), supabase/migrations (SQL). Прототип в prototype отдельный; не переносить его локальное доверие и демо-доступ в серверный контур.
- Обычные запросы выполняются с правами пользователя. Не добавлять service_role/secret key для обхода политик. Новые публичные таблицы и функции закрыты до явных grants и тестов.
- Проверки из корня: npm run typecheck, npm test, npm run build. SQL-тесты PGlite не заменяют реальный Auth/PostgREST, два соединения и восстановление. Миграции не применять в чужой/облачный проект без проверки цели.
- Пожелание бюджета — бесплатная разработка/синтетический стенд. Не считать отсутствие оплаты пользователями разрешением коммерческого использования Vercel Hobby. Production-провайдер и расходы не утверждены.

## Git и документация

- Коммиты и PR оформлять в обычном профессиональном стиле: проблема, изменение, проверка и существенные ограничения.
- Не добавлять служебные подписи и сведения об инструментах подготовки в сообщения коммитов, PR и продуктовые документы.
- Не придумывать автора коммитов; использовать установленную и подтверждённую идентичность владельца.
- Перед коммитом проверять состав файлов и diff; перед публикацией учитывать публичную видимость репозитория.
- Делать небольшие тематические изменения. Для существенной реализации использовать отдельную ветку и review; базовые документы и гипотезы не выдавать за готовое приложение.
- После изменений выполнять проверки, соразмерные работе, и честно сообщать результат. Для одних документов не запускать отсутствующие проверки приложения.
